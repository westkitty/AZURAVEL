# AZURAVEL — Scrambled Language Master Creation Prompt

> **Target:** A fresh ChatGPT conversation  
> **Objective:** Create a functional constructed language based on reversible word scrambling, with a precise Azure visual identity and genuine barcode encoding.

## Master Prompt

You are a computational linguist, cryptographer, typographic systems designer, and experimental language architect.

### Mission

Invent a completely original, coherent, functional constructed language whose defining feature is **word scrambling**. It must not be an English substitution cipher, random anagrams, or decorative gibberish. The rearrangement of letters, syllables, and structural segments must perform meaningful grammatical operations. Make the language learnable, generative, and reversible where specified.

### Identity and visual requirements

- Working name: **AZURAVEL**; replace only if a demonstrably stronger name emerges.
- Primary Azure: **`#007FFF`** (standard Azure blue).
- Alternative: **`#0078D4`** (Microsoft Azure blue), only if the user selects that identity.
- Supporting colors: deep navy and white, with accessible contrast.
- Default machine-readable barcode: **Code 128**.
- Barcodes must have correct start/stop patterns, checksums, quiet zones, and module proportions. Prefer black bars on white for scanning; use Azure in framing and interface elements.
- Never label decorative stripes as scannable. If an existing barcode standard or reference is supplied, inspect it before fixing the format.

### Fundamental linguistic principle

Meaning depends on **lexical material** (phonemes or syllables present) and **arrangement** (their order, grouping, and transformation history). A root retains recognizable conceptual identity through permitted permutations. For illustration only, `ABCD` could represent a stable state, `BACD` its beginning, `ACBD` its alteration, and `DCBA` its reversal. Design a more systematic and productive mechanism rather than adopting these examples uncritically.

### Phase 1 — Language foundations

Define the phoneme inventory, syllable structure, permissible sound combinations, pronunciation, stress, word boundaries, root formation, grammatical categories, sentence structure, and semantic composition. Every valid surface word must be pronounceable.

### Phase 2 — Scrambling engine

Evaluate full reversal, adjacent transposition, cyclic rotation, syllable exchange, segment inversion, nested scrambling, partial scrambling, ordered permutation chains, repetition, and compound-root interleaving. Adopt only a minimal, expressive subset. For each operation document its formal definition, grammatical function, semantic effect, pronunciation effect, inverse (if any), composition rules, examples, and illegal applications. Specify precedence and deterministic collision handling. The same operation must have consistent meaning across roots.

### Phase 3 — Formal grammar

Explain how the language expresses tense, aspect, negation, questions, commands, number, possession, identity, agency, causation, possibility, certainty, conditionals, reciprocity, and emphasis. Use particles where scrambling alone would be ambiguous or unlearnable. Distinguish lexical meaning from grammatical meaning.

### Phase 4 — Writing system

Create a script with systematic mappings to the spoken language. Explore modular letterforms, reversible characters, segment blocks, permutation paths, and Azure transformation markers. Specify direction, spacing, punctuation, and capitalization equivalents. Do not assign arbitrary glyph art to every vocabulary item: readers must be able to construct unfamiliar words from known rules.

### Phase 5 — Barcode architecture

For every valid lexical form, define: canonical text, transformation metadata, encoded payload, human-readable label, decoding procedure, version identifier, and validation method. Establish an unambiguous versioned serialization format. Show one root and multiple permutations producing distinct payloads. Produce actual Code 128 examples only when encoding/rendering tools are available; otherwise provide exact payload strings and an implementation-ready specification. Never fabricate checksum or scan-test results.

### Phase 6 — Dictionary

Create **exactly 100 distinct lexical roots**, organized into semantic domains such as identity, relationships, movement, space, time, creation, knowledge, emotion, nature, change, logic, and possibility. For every root provide canonical spelling, pronunciation, core meaning, grammatical behavior, at least three valid scrambled forms with their meanings, derivations, and an example sentence. Permutations do **not** count as additional roots.

### Phase 7 — Sentences

Write **20 progressively complex sentences**, including a greeting, question, negation, command, past event, future intention, conditional, reciprocal relationship, philosophical statement, and short poetic passage. Give original text, pronunciation, morpheme-by-morpheme gloss, natural English translation, and explanation. Demonstrate how changing one permutation changes a sentence's meaning.

### Phase 8 — Visual atlas

Design a polished futuristic linguistic field guide and cryptographic typography laboratory. Use exact Azure hex values, deep navy, crisp typography, readable diagrams, and genuine barcode samples. Include distinct sections for phonology, scrambling operations, word anatomy, grammar, barcode architecture, vocabulary, and translation. Do not use generic fantasy runes or unreadable ornamental text. Treat the formal text specification—not generated images—as authoritative.

### Phase 9 — Interactive translator

Specify an interface and algorithms for English-to-language mapping (within documented vocabulary limits), language-to-English parsing, word scrambling, pronunciation, root inspection, transformation history, barcode encoding/decoding, sentence construction, and validation feedback. Unknown terms must be reported, not silently invented. If code execution is available, build a small working reference implementation of reversible transformations and barcode payload serialization.

### Phase 10 — Adversarial verification

Test root and permutation collisions, parsing ambiguity, pronunciation legality, reversibility, contradictory rules, semantic inconsistency, runaway word growth, duplicate roots, invalid barcode payloads, checksum errors, lossy decoding, and glyph mapping inconsistency. Create **at least 30 test cases** including edge cases. Run tests where tools permit, repair confirmed defects, and clearly distinguish verified, failed, and untested claims.

### Required deliverables

1. Language name and identity.
2. Complete design specification.
3. Formal scrambling rulebook.
4. Phonology and writing system.
5. Exactly 100-root dictionary.
6. Barcode encoding/decoding specification.
7. Twenty analyzed sentences.
8. Visual atlas or render-ready specification.
9. Translator architecture and working prototype when supported.
10. Honest validation report.

### Execution rules

Start with the linguistic architecture, not decorative artwork. Keep the formal specification authoritative. Make reasonable creative choices without unnecessary questions. Treat the Azure and barcode defaults above as provisional if the user later supplies an authoritative reference. If output limits prevent completion in one response, deliver coherent numbered stages and explicitly identify unfinished work. Never invent tests, scan results, generated files, or implementation success.

### Acceptance test

A trained reader must be able to encounter an unseen valid word, pronounce it, identify its root, reverse its transformations, determine grammatical role and meaning, serialize it into a barcode payload, decode the payload losslessly, use the word in a valid sentence, and explain how each transformation changes meaning.

**The language must work, not merely look impressive. Begin.**
